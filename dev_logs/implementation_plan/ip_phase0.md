# 多Agent并行开发执行计划

本项目旨在开发一个“日程管理 + AI日记助手”的桌面级应用程序。为了高效完成项目，我们将根据 `PRD.md`、`CONTEXT.md` 以及 `issue-1` 到 `issue-8` 的任务拆分，设计一套多Agent（多智能体）并行开发的执行方案。

## User Review Required

> [!IMPORTANT]
> **技术栈确认**
> 
> 目前项目目录中存在 `venv` 和基础的 `package.json`，根据 PRD 的描述，我们建议采用以下技术栈进行开发：
> - **前端 UI 与主进程**：基于 `Electron` + `React` (或 `Vue`) + `Vite` 构建，负责界面展示与基本逻辑控制。
> - **后端数据存储**：采用 `SQLite` 作为本地数据库。
> - **系统级钩子服务**：采用 `Python` (配合 `pywin32` 等库) 作为一个后台常驻服务，处理获取当前活动窗口和判断系统休眠状态（这能够直接利用现有的 `venv` 环境，并且 Python 在 Windows API 抓取方面生态更完善）。前端主进程与 Python 脚本通过本地端口/标准输入输出通信。
> 
> **您是否同意该技术栈方案？如果有指定的框架，请告知我。**

## Proposed Changes

整个开发流程将分为五个阶段推进，确保具有依赖关系的任务有序进行，同时最大化利用多 Agent 的并行能力。

---

### Phase 0: 初始环境搭建 (Initial Setup)
- 运行工作流 `/initial`。
- 初始化 Git 仓库，建立项目骨架（例如 Electron + Vite 模板）。
- 安装必要的 Node.js 依赖包与 Python 依赖（如 `fastapi` / `pywin32` / `sqlite3` 等）。
- 制定前后端（或者说 Electron 与 Python 进程）通信的契约与数据库（SQLite）初始表结构。

---

### Phase 1: 核心独立模块并行开发
本阶段没有前置依赖，将启动两个子Agent并行开发：

#### Agent A (后端/全栈): 处理 Issue-1
- 目标：建立基础数据存储方案，实现日程的增删改查。
- 产出：SQLite `Schedule` 表结构，以及能在前端完成基础 CRUD 操作的页面骨架。

#### Agent B (系统底层/后端): 处理 Issue-2
- 目标：开发周期性获取前台窗口名称的后台服务，以及隐私白名单面板。
- 产出：Python `AppTracker` 服务，SQLite `AppUsage` / `Whitelist` 表，和用于授权白名单的 UI 界面。

---

### Phase 2: 衍生独立模块并行开发
本阶段基于 Phase 1 的成果进行扩展：

#### Agent A: 处理 Issue-3 (基于 Issue-1)
- 目标：构建固定日程的模板配置，及当天日程实例生成引擎逻辑。
- 产出：独立于普通日程的模板表，调度引擎实现，实例编辑功能（不污染原模板）。

#### Agent B: 处理 Issue-7 (基于 Issue-2)
- 目标：利用 Issue-2 已有的系统休眠感知等钩子，构建久坐与用眼疲劳健康提醒倒计时。
- 产出：倒计时逻辑，原生桌面提醒窗口/系统提醒交互。

---

### Phase 3: 数据聚合与主线贯通
此阶段需要汇总 Phase 1 与 Phase 2 的成果，由主 Agent（或单一子 Agent）重点攻坚：

#### Agent A (核心攻坚): 处理 Issue-4
- 目标：构建日记草稿面板，大模型请求封装，上传及最终定稿机制。
- 产出：从 DB 中读取日程与应用使用情况，构建 Prompt 传给大模型（OpenAI API兼容接口），并保存 `Finalized Diary`。

#### Agent B: 处理 Issue-8 (基于 Issue-1, Issue-7)
- 目标：构建独立悬浮桌面组件。
- 产出：Electron 开启的透明置顶无边框小窗口，实时读取最新日程与健康状态倒计时。

---

### Phase 4: 闭环与历史数据功能并行
最后完善系统流程和用户历史数据查询：

#### Agent A: 处理 Issue-5
- 目标：定时任务自动上传和降级登记。
- 产出：夜间自动流转状态机的后台定时器逻辑。

#### Agent B: 处理 Issue-6
- 目标：全局日历视图与历史日记二次编辑功能。
- 产出：全年日历组件，日历数据读取与文本修改的页面闭环。

---

## Verification Plan

### Automated Tests
- 为 Python 服务编写基本的单元测试，验证进程名称获取的准确性与白名单过滤逻辑。
- 为日记状态机（Draft -> Generated -> Finalized）编写关键流转路径的测试。

### Manual Verification
- 手动模拟开启应用，查看白名单外应用是否被屏蔽。
- 触发系统的休眠机制，验证健康计时器是否正确挂起与恢复。
- 手动触及“自动上传”设定时间，观察后台是否静默执行，以及 UI 是否弹出预期的弹窗（或不弹窗）。

请确认上述实施计划及技术栈方案，批准后我将开始搭建 Phase 0 基础环境并调用子Agent执行 Phase 1。
